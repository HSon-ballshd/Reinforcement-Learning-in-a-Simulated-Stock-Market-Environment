# 2.13 Dealing with Inaccurate Models

## Why models go wrong

A **model** in RL stores the agent's experience of the environment: for each `(state, action)`, the next state and reward that were actually observed. The model is **inaccurate** when what it stores differs from what would actually happen if the agent repeated that action.

Two common ways this happens:

- **Incomplete model.** The agent simply hasn't tried most `(s, a)` pairs yet, so the model has no transition stored for them. The model "isn't wrong" — it just can't produce a next step or reward, so it cannot be used for planning in those spots.
- **Stale / wrong model.** The environment has changed since the data was collected. The same action now leads somewhere new, but the model still reports the old next state and reward. As the agent gathers fresh experience, it can patch the model and resume planning.

> Analogy: an **inaccurate model is an outdated map**. If the city rebuilds a road, your map sends you into a wall until you drive the route again and redraw it.

## The cost of planning with a bad model

Planning means running simulated updates against the model to improve the value function. If the model is wrong, those simulated updates can push the value function (and therefore the policy) in the **wrong direction** with respect to the true environment. The agent is essentially **hallucinating consequences** and then trusting them.

A small worked example from the lecture: a rabbit's model initially says "move right" from the leftmost cell goes straight to the carrot. Reality takes the rabbit to the middle square instead. Until the model is corrected, any plan built on the old transition is misleading.

Because of this risk, the agent has a **vested interest in keeping its model accurate**.

## A new exploration–exploitation trade-off

With a fixed environment, exploring more only costs time. With a **changing environment**, things shift: the model can become wrong at *any* moment, and it stays wrong until the agent revisits the affected states and updates the model.

This creates a second exploration–exploitation trade-off:

- **Explore** to detect and correct model errors, OR
- **Exploit** the current (possibly stale) model and behave as if it is still right.

The practical rule of thumb: **visit states you haven't been to in a while**, because that is exactly where the model is most likely to be out of date.

## Exploration bonus: a reward-shaped cure

To bias planning toward long-untried states, the agent inflates the rewards used during planning:

```
r_planning = r_model + κ * sqrt(τ)
```

Where:
- `r_model` is the reward the model reports for the transition.
- `τ` (tau) is the **number of time steps since that `(s, a)` pair was last visited in the real environment**.
- `κ` (kappa) is a small constant that controls how much the bonus matters.
  - If `κ = 0`, the bonus is ignored and the agent behaves like plain Dyna-Q.
- `τ` is **only** updated by real environment steps, never by simulated planning steps — otherwise the agent could "visit" a state in its head and cancel the bonus, defeating the point.

By making long-untried `(s, a)` look more attractive in imagined rollouts, planning naturally drifts toward the parts of the world the model knows least about.

> Analogy: think of it as **Google Maps nudging you to "explore a road you haven't driven lately"** because the traffic data might be outdated. The bonus is that nudge.

## Dyna-Q+

Adding the exploration bonus to the planning step of Dyna turns it into **Dyna-Q+**. Mechanically, the direct RL loop and the model-learning step are identical to Dyna-Q; the only difference is the bonus applied to the reward inside the n planning updates.

## Dyna-Q vs Dyna-Q+

| Aspect | Dyna-Q | Dyna-Q+ |
|---|---|---|
| Exploration in planning | No time-based bonus; uses a fixed exploration mechanism | Adds `κ * sqrt(τ)` bonus that grows with time since last visit |
| Planning targets | Updates any previously-seen `(s, a)` uniformly | Implicitly prioritizes long-untried `(s, a)` pairs through the bonus |
| Reward signal in planning | Uses the model's reward as-is | Inflates reward for stale transitions |
| Best for | Stationary environments | Changing / non-stationary environments |

In short: **Dyna-Q trusts the model and explores only at the acting step; Dyna-Q+ distrusts the model and forces planning to keep checking the world.**

## Key Takeaways

- A model is inaccurate when stored transitions differ from what the environment actually does — either because they were never observed (**incomplete**) or because the environment has changed (**stale**).
- Planning against an inaccurate model can drive the value function and policy in the **wrong direction**, so the agent should care about model quality.
- A **second exploration–exploitation trade-off** appears in non-stationary worlds: explore to repair the model, or exploit the current (possibly wrong) policy.
- The **exploration bonus** `r + κ * sqrt(τ)` makes long-untried `(s, a)` pairs look attractive during planning, encouraging revisits that detect and fix staleness. `τ` is incremented only by real steps, not imagined ones.
- **Dyna-Q+** = Dyna-Q + this time-dependent exploration bonus inside the planning loop.
- Compared to Dyna-Q, Dyna-Q+ is more robust to **changing environments** because planning is actively steered toward the parts of the world most likely to be out of date.
- Setting `κ = 0` reduces Dyna-Q+ back to Dyna-Q — the bonus is the entire behavioral difference.
